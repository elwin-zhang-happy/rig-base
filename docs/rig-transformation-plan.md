# 以 rig 为基础集成组件：整体架构设计

## Context

目标是把 rig 改造成自有产品的基础集成组件，覆盖三种工作场景：

1. 单次 agent 调用，包含工具调用、MCP、skill。
2. 图结构编排。
3. 类似 pi 的自主 agent 循环。

两条硬要求：

1. 每次执行有持久化落地，可重复、可断点续跑。
2. 全程可观测：token 消耗、调用次数、接口状态、工具执行情况，以及执行和持久化本身的健康度。

本文件只给设计思路、分层、架构和每个决策的原因，不给代码实现。

---

## 0. 需求追溯

| 需求 | 设计落点 | 如何验证 |
|---|---|---|
| 每次执行有持久化落地 | L1 的 effect 记录、L2 的执行单元状态、L3 的节点状态，统一写入持久化面（3.4、7.1） | 任意一次 run 都能只凭日志重建 |
| 可重复 | 追加日志、确定性 effect id、回放与重跑分离、工具与 skill 快照（5.13、5.14、7.2） | 同一份日志回放两次，事件序列一致 |
| 断点继续执行 | 检查点（快照 + 游标）、在途 effect 三策略、人工中断挂起（5.10、5.11、5.12、7.2） | 在模型调用和工具调用之间杀进程，恢复后不重复已完成 effect |
| 人工介入：工具、模型、节点 | 统一中断点：L2 的工具门和模型门，L3 的节点门；`human_requested` / `human_answered` 事件加检查点（5.24、7.1、7.2） | 挂起后换进程、换机器恢复，决策可回放 |
| token 消耗 | 8.3 用量指标：输入、输出、缓存读写、推理、预算、上下文占用 | 按 run、节点、轮次、模型回答花了多少 |
| 调用次数 | 8.4 调用次数指标：模型、工具、轮次、节点、重试、人工介入 | 回答调了几次、重试几次、为什么重试 |
| 接口状态 | 8.5 接口状态指标：耗时、首 token、HTTP 类别、错误种类、限流、request id | 回答哪个 provider 慢、哪个错误、能否对上 provider 侧记录 |
| tool 执行情况 | 8.6 工具执行指标：十种状态、耗时、输出大小、去重、配对错误 | 回答每个工具是成功、失败、被拒、跳过还是不确定 |
| 执行与持久化健康 | 8.7：检查点、日志、恢复、在途调用、挂起积压 | 回答系统本身是否可靠，而不只是“有文件” |

## 1. 核心判断

> rig 是**数据平面**：消息、请求/响应、wire/driver、工具契约、会话、effect 记录。
> 你的产品需要**控制平面**：日志、检查点、工作流图、策略、观测。
> 三个场景不是三套引擎，而是同一个执行单元的三种组合；每个执行单元由同一个 Effect 原语构成。

这个判断来自一个事实：rig 已经把“和外部世界交互”抽象得很干净，但没有把“一次执行如何被记录、恢复、编排”做成完整运行时。`rig-ecs` 做了后者，但它绑定 Bevy，且面向终端编码 agent，不适合作为通用集成组件的内核。

因此改造的总方向是：**保留 rig 的协议和数据模型，自己补控制平面**。

---

## 2. 设计原则

| 原则 | 内容 | 原因 |
|---|---|---|
| P1 事实与决策分离 | 外部事实写日志，控制决策由解释器做 | 事实可重放，决策可替换；混在一起就无法复现 |
| P2 边界必须可序列化 | 跨 run、跨进程、跨节点的数据只能是稳定格式 | 断点续跑、回放、跨语言、跨版本都要求边界上没有活对象 |
| P3 控制流是数据 | 图、策略、预算都是可序列化的描述 | 描述可以存储、校验、比较、迁移；运行中的对象不能 |
| P4 状态分层 | 协议态、会话态、执行态分开存 | 生命周期不同，混存会导致恢复粒度过粗或过细 |
| P5 幂等优先 | 默认假设任何外部调用可能执行两次 | 跨进程无法做到恰好一次，只能做到可去重 |
| P6 观测是投影 | 日志是唯一事实来源，trace 和指标是它的投影 | 多套事实来源必然互相矛盾 |
| P7 窄接口 | 对外只暴露少量执行入口和事件流 | 集成组件的价值在稳定边界，不在功能数量 |

## 3. 分层架构

### 3.1 分层判据

分层的判据不是“代码放在哪个目录”，而是**组合关系**：

- 上一层把下一层组合成一个更大的行为单元。
- 依赖只能向下，不能反向。
- 每一层只回答一个问题，不承担上下层的问题。

为什么用组合关系而不是职责清单：职责可以重叠，组合关系不会。只要出现“上层调用下层，下层又回调上层”，就说明层画错了。按组合关系画，依赖方向天然唯一。

### 3.2 六个层（L0 到 L5）

| 层 | 名称 | 回答的问题 | 组成 | 依赖 |
|---|---|---|---|---|
| L5 | 宿主层 | 谁发起、谁消费 | HTTP API、CLI、Web、任务系统 | L4 |
| L4 | 应用层 | 一次业务用例如何开始、恢复、观察 | run_agent、run_workflow、resume、observe；句柄负责状态、取消、事件流 | L3、L2、横切面 |
| L3 | 编排层 | 多个执行单元如何组合 | 工作流定义、解释器、分支、并行、子图、节点门 | L2 |
| L2 | 执行层 | 一个执行单元如何推进 | 单次执行与 agent 循环、停止/预算/压缩/转向、工具门/模型门、工具来源装配 | L1 |
| L1 | 调用层 | 一次外部交互如何完成 | Effect 调度、模型调用、工具执行、MCP、skill 加载、人工交互 | L0 |
| L0 | 契约层 | 世界里有什么、长什么形状 | 消息、请求/响应、工具、会话、effect 记录、run 状态 | 无 |

```
┌──────────────────────────────────────────────┐
│ L5 宿主层                                     │
│ API / CLI / Web / 任务系统                    │
└───────────────────┬──────────────────────────┘
┌───────────────────▼──────────────────────────┐
│ L4 应用层                                     │
│ 用例编排：开始、恢复、取消、订阅               │
└───────────┬──────────────────────┬───────────┘
            │ 无图                  │ 有图
            │                       ▼
            │            ┌──────────────────────┐
            │            │ L3 编排层             │
            │            │ 节点 / 边 / 并行      │
            │            └──────────┬───────────┘
            ▼                       ▼
┌──────────────────────────────────────────────┐
│ L2 执行层                                     │
│ 单次执行 / AgentRun 循环 / 策略                │
└───────────────────┬──────────────────────────┘
┌───────────────────▼──────────────────────────┐
│ L1 调用层                                     │
│ Effect 调度 / 模型 / 工具 / MCP / skill        │
└───────────────────┬──────────────────────────┘
┌───────────────────▼──────────────────────────┐
│ L0 契约层                                     │
│ 消息 / 请求 / 响应 / 工具 / 会话 / effect 记录 │
└──────────────────────────────────────────────┘
```

图中的 L3 只依赖 L2，L2 依赖 L1，L1 依赖 L0。L4 有两个入口，是因为单次调用不需要经过图解释器；但两条路径在 L2 汇合，执行语义一致。L3 不直接调用 L1：模型节点和工具节点在 L2 里都是单次执行单元。

### 3.3 为什么是这个顺序

- L0 在最底，因为所有其他层都要按它的形状交换数据；它不依赖任何上层。
- L1 在 L0 之上，因为它把契约层的一次请求变成一次真实外部交互，再把结果变回契约。
- L2 在 L1 之上，因为执行单元是“一次或多次调用 + 状态推进”，它组合调用，不实现调用。
- L3 在 L2 之上，因为图是“多个执行单元的组合 + 路由”，它组合执行单元，不实现执行。
- L4 在 L3 之上，因为应用层只负责用例生命周期：开始、恢复、取消、订阅，不参与执行细节。
- L5 在最上，因为它只消费 L4 的能力，不定义任何执行语义。

这条顺序还可以用一句话检验：**每一层只能使用它下面层的公开契约，不能看到更下面层的实现。** L4 是组合根，可以在 L3 和 L2 两个公开契约之间选择；其余层只使用紧邻下层。违反这句话，层就没画对。

### 3.4 两个横切面，不是两层

持久化和可观测性被单独列出来，但它们**不是层**。

| 横切面 | 回答的问题 | 组成 | 依赖 |
|---|---|---|---|
| 持久化面 | 发生过什么、如何恢复 | Journal、Checkpoint、Replay、SessionStore | L0 |
| 可观测面 | 正在发生什么、为什么慢/错 | 用量、调用次数、接口状态、工具状态、执行与持久化健康度 | L0 |

为什么不是层：

1. **它们不组合数据，只保存或观察数据。** 层是行为的组合关系；横切面是旁路服务。把旁路服务画进主栈，会让所有上层都“穿过”它，产生假的依赖。
2. 它们被多层调用，而不是被一层独占。L1 记录 effect（包括人工 effect），L2 记录执行步，L3 记录节点，L4 记录用例。它们出现在多个层，属于“面”，不属于“层”。
3. **它们的实现是边缘适配器。** 文件、数据库、OTLP 都是可替换的实现；层不应该依赖具体实现。
4. **它们只依赖 L0。** 因为持久化的前提是所有边界数据都可序列化；观测的载荷也是契约类型。它们不依赖 L1 以上的任何东西，否则就会反向耦合。

所以正确的画法是：

```
主栈（依赖只向下）:
  L5 → L4 → L3 → L2 → L1 → L0
  L4 可按用例直接选择 L2

横切面（被各层调用，但只依赖 L0）:
  L1、L2、L3、L4 ──→ 持久化面 ──→ L0
  L1、L2、L3、L4 ──→ 可观测面 ──→ L0
```

横切面从各层接收事件，只依赖 L0；它们不改变主栈的依赖方向。

### 3.5 依赖规则

人工 effect 是一种 effect，不是独立通道：门是 L2/L3 的策略，effect 调度永远在 L1。审批不会打断工具 effect、人工交互也不会跨层回调，依赖方向因此成立。

| 规则 | 内容 | 原因 |
|---|---|---|
| R1 | 上层只能依赖下层，禁止反向；除 L4 这个组合根外，只依赖紧邻下层 | 保证方向唯一，避免回调环；L4 需要按用例在 L3 和 L2 之间选择 |
| R2 | 同层模块只能通过公开契约互相依赖 | 防止层内隐式耦合 |
| R3 | 横切面只依赖 L0，上层通过端口使用，不依赖实现 | 持久化和观测可替换、可测试 |
| R4 | 适配器向内依赖端口，宿主不直接依赖适配器 | provider、MCP、存储都能换成假实现 |
| R5 | 任何跨层数据必须是 L0 的可序列化类型 | 持久化、回放、跨进程的前提 |
| R6 | L0 不依赖 async runtime、IO、具体 provider | 契约可移植到测试、WASM、其他语言 |

R3 是对 R1 的补充。横切面不是层，所以“只依赖 L0”不违反“上层依赖下层”；它恰恰保证了横切面不会偷偷依赖上层。

### 3.6 每层回答一个问题

| 层 | 只回答 | 不回答 |
|---|---|---|
| L0 | 数据长什么样 | 怎么调用、怎么编排 |
| L1 | 一次外部交互怎么完成 | 下一步做什么、多个执行怎么组合 |
| L2 | 一个执行单元怎么推进（单次或循环） | 多个执行单元怎么路由 |
| L3 | 多个执行单元怎么组合 | 单个执行单元内部怎么推进 |
| L4 | 一次用例怎么开始和结束 | 执行细节、节点调度 |
| L5 | 用户怎么使用 | 任何执行语义 |

这张表的用途是判断新功能该放哪层：如果它同时回答两个问题，说明它应该被拆开。

### 3.7 一次执行如何穿过各层

```
宿主发起
  → L4 创建 run：生成 run_id，选用例（单 agent 或工作流）
  → L3（有图时）选下一个节点
  → L2 推进执行单元：取下一步（单次调用或 AgentRun）
  → L1 调度 effect：模型调用 / 工具 / MCP / skill / 人工
  → L0 表达请求和响应
  → 适配器执行真实交互
  ← 结果回到 L1，归一化
  → 持久化面：写 effect 事件
  → L2 更新执行单元状态
  → L3 更新工作流状态
  → 持久化面：写节点事件、检查点
  → 可观测面：发出 trace、指标、业务事实
  → L4 把事件流交给宿主
```

### 3.8 状态归属

| 状态 | 归属层 | 是否持久化 | 原因 |
|---|---|---|---|
| 消息、请求、响应、工具定义 | L0 | 是 | 是回放和恢复的载荷 |
| AgentRun 协议状态 | L0 的形状，L2 的推进 | 是 | 断点续跑的最小单元 |
| 工作流游标、前沿、节点输出 | L3 | 是 | 图级恢复 |
| 在途调用句柄 | L1 | 否 | 进程内对象，崩溃即失效 |
| 策略计数器 | L2 | 是（随检查点） | 恢复后预算和停止条件要延续 |
| 会话 | 横切面 | 是 | 跨 run 的记忆 |
| trace、指标 | 可观测面 | 按保留策略 | 诊断用，不是事实来源 |

## 4. 最小单元：七个契约

这些是 L0 的内容。每个之所以是“单元”，是因为它同时满足三个条件：边界清晰、可序列化、被多个上层复用。

### 4.1 消息

- 内容：用户消息、助手消息、工具调用、工具结果、推理内容、图片、文档。
- 为什么是单元：它是所有 provider、工具、MCP、日志、UI 的共同语言。换掉它，所有适配层都要改。
- 边界：只表达“模型看到/产出了什么”，不表达“为什么”。

### 4.2 请求与响应

- 内容：一次模型调用的输入和输出，加上用量和结束原因。
- 为什么是单元：它是 effect 的载荷。录制、回放、重试、预算都以它为单位。
- 边界：不包含 provider 细节。provider 差异在 wire 里。

### 4.3 Wire / Decoder / Fold / Transport

- 内容：编码请求、切分响应帧、把事件折叠成响应、发送字节。
- 为什么是单元：这四步把“厂商差异”和“网络 IO”彻底隔离。换厂商只换 wire，换录制只换 transport。
- 边界：wire 是纯函数，transport 是唯一 IO。

### 4.4 工具

- 内容：名称、描述、参数 schema、足迹、调用、归一化结果。
- 为什么是单元：它是模型能做的第二类动作。MCP 工具、skill 加载、本地命令都落在这里。
- 边界：工具不负责编排、不负责持久化、不负责审批。这些是外层策略。

### 4.5 会话

- 内容：带 id 的消息条目、旁注、变更 outbox、工具调用配对。
- 为什么是单元：它把“历史”从“一次执行”里分离出来。一次会话可以有很多次执行。
- 边界：只追加，不解释业务含义。

### 4.6 Run 状态

- 内容：轮数、历史、用量、待处理工具调用、协议状态。
- 为什么是单元：它是单 agent 循环的最小可序列化状态。没有它，断点续跑只能停在“整次调用”粒度。
- 边界：只描述状态，不持有模型、工具、hook、future。推进逻辑属于 L2。

### 4.7 EffectRecord

- 内容：调度 id、处理器 key、effect 类型、结果或错误、父调用、作用域。
- 为什么是单元：它是“发生过什么”的最小事实。回放、审计、观测、去重都以它为单位。
- 边界：记录的是归一化后的请求和结果，不是原始报文。

### 4.8 学习顺序与自检

| 顺序 | 单元 | rig 里的参考位置 | 要看到的不变量 | 自检问题 |
|---|---|---|---|---|
| 1 | 消息 | `rig-core/src/completion/message.rs` | 工具调用和结果是消息内容，不是独立通道 | 一条工具调用消息能否不依赖 provider 表达 |
| 2 | 请求/响应 | `rig-core/src/completion/request.rs` | 请求是纯数据，响应带用量和结束原因 | 去掉 provider 名字后，请求还完整吗 |
| 3 | wire/driver | `rig-core/src/wire.rs`、`driver.rs` | encode 不碰网络，transport 是唯一 IO | 换成回放传输，上层要不要改 |
| 4 | 工具 | `rig-core/src/tool/contextual.rs`、`rig-agent/src/tool/registry.rs` | 工具是静态契约，擦除后是动态契约 | MCP 工具能否不新增契约接入 |
| 5 | 会话 | `rig-core/src/conversation/mod.rs` | 变更可折叠，调用和结果可配对 | 重放一段会话能否得到同一个值 |
| 6 | run 状态 | `rig-agent/src/run/mod.rs` | 状态机不持有 IO，序列化后能继续 | 中途落盘再加载，下一步是否一致 |
| 7 | effect 记录 | `rig-core/src/effect/mod.rs`、`serve/recorder.rs` | 一次外部交互是一条可重放事实 | 缺记录时回放是否报错 |
| 8 | 观测 | `rig-core/src/observe/mod.rs`、`telemetry/mod.rs`、`rig-agent/src/agent/hook.rs` | 事实、诊断、干预是三种东西 | 能否从一条指标定位到一次调用 |
| 9 | ECS 参考 | `rig-ecs/src/stage.rs`、`session_log.rs`、`restore.rs` | 单一 effect 通道、七阶段、恢复对账 | 哪些机制值得抄，哪些是 Bevy 专属 |

为什么是这个顺序：每个单元都是下一个单元的前提。先有消息才能有请求，先有工具契约才能有执行单元，先有可序列化状态才能有图和恢复。反过来读，会把现象当成原因。

学习方式：每一步只回答两个问题，它的边界是什么，它依赖谁。先看数据形状和调用方向，再看实现细节。

## 5. 关键设计决策

每条包含：决策、原因、代价、什么情况下改变。

### 5.1 采用模式：依赖 rig，不 fork 内核

**决策**：依赖 `rig-core`、`rig-agent` 的 run 模块、`rig-rmcp`、`rig-memory`。不引入 `rig-ecs`、`rig-harness`、`plugins`。在自己的仓库新增 `your-*` 模块。

**原因**：

- rig-core 的 provider 覆盖和 wire 设计已经过大量录制测试验证，重写没有收益。
- `rig-agent::run` 是 sans-IO 状态机，正好是 L2 需要的原语。
- `rig-ecs` 精确锁 Bevy 版本，引入它等于把整个产品变成 Bevy App，而三种场景都不需要 Bevy。
- 新增模块可以继续合并上游，不会因为改内核产生长期冲突。

**代价**：上游 API 变化需要跟进；高层抽象不一定完全贴合策略。

**改变条件**：如果产品本身就是 Bevy 应用，或者需要在每一帧内做运行中介入，那么 `rig-ecs` 的七阶段和 hold 机制值得直接用。

### 5.2 执行原语：Effect 是唯一的

**决策**：模型调用、工具调用、MCP 调用、skill 加载、人工审批，全部走 L1 的同一个 effect 调度入口。人工审批是一种 effect 类型，门只决定何时发起它。

**原因**：

- 一套调度意味着录制、回放、重试、预算、审批、观测只实现一次。
- 如果 MCP 或 skill 有独立通道，所有横切关注点都会翻倍，且行为容易不一致。
- 人工审批也作为 effect 记录：门决定发起，L1 调度，`begin` 是 `human_requested`，`settled` 是 `human_answered`。审批因此自动获得录制、回放、超时和观测。
- rig 的 `Recorder` 和 `EffectRecord` 已经是按这个假设设计的。

**代价**：effect 的载荷要能表达多种类型；调度层需要一点分发逻辑。

**改变条件**：出现无法用一次请求/响应表达的交互，例如长连接订阅。那时它应该成为 effect 的一种新类型，而不是新通道。

### 5.3 事实来源：Journal 是唯一的

**决策**：所有执行事实先写 journal，再产生用户可见效果。trace、指标、UI 都是 journal 的投影。

**原因**：

- 断点续跑需要知道“崩溃前到底发生了什么”，只有追加日志能回答。
- 审计和多套导出需要同一个事实来源，否则数据对不上。
- 日志可以重放，内存状态和数据库行不行。

**代价**：写入放大；需要保留策略和压缩。

**改变条件**：如果产品只做一次性短任务，不需要恢复，那么普通日志足够。

### 5.4 图的形态：数据 + 解释器

**决策**：工作流是可序列化的数据（节点、边、状态 schema、版本），L3 是解释它的运行时。不用运行中的对象表示节点。

**原因**：

- 图要能存、能校验、能比较、能迁移、能跨语言。运行中的对象都做不到。
- 解释器可以统一处理检查点、重试、取消、观测。节点自己实现这些，行为必然不一致。
- 图是产品资产，节点是代码资产。分开后，产品可以在不重新编译的情况下改流程。

**代价**：没有编译期类型检查；需要用 schema 校验和运行时错误处理补上。

**改变条件**：如果节点类型永远只有两三种，且不跨进程，硬编码的组合函数更简单。但场景二明确要求图结构，所以不适用。

### 5.5 节点边界：只传 JSON

**决策**：节点输入输出是 JSON，配 JSON Schema 声明；节点之间不传运行中的强类型值。

**原因**：

- 序列化是断点续跑和回放的前提。
- JSON 让图可以被非 Rust 的宿主或工具读取、生成、调试。
- schema 提供了运行时的结构校验，弥补失去的编译期检查。

**代价**：多一次序列化/反序列化；复杂结构的类型安全靠 schema 和测试。

**改变条件**：单进程、单语言、不需要恢复的内部流水线可以传强类型值。

### 5.6 执行单元：单次和循环是同一种东西

**决策**：L2 只提供一种执行单元。单次调用是“一步执行”，agent 循环是“多步执行”，两者共用同一个 run 状态机和同一套策略接口。

**原因**：

- 单次调用和循环的差别只是步数、策略和编排，不是执行模型。
- 统一后，工具配对、坏参数反馈、流式输出、用量累计、断点检查只实现一次。
- 图节点无论包的是模型、工具还是 agent，都是同一种执行单元，L3 不需要为不同节点写不同的调度。
- 执行单元的状态可序列化，天然支持断点。

**代价**：需要一个统一的执行单元抽象，单次调用会多一层很薄的包装。

**改变条件**：如果单次调用的性能要求极端，可以在 L2 内部直通 L1，但对外语义不变。

### 5.7 自主循环：策略，不是新引擎

**决策**：自主性通过四组策略实现：停止、预算、压缩、转向。子 agent 通过图或 agent-as-tool 实现。

**原因**：

- 模型不能可靠地自己停下来。停止条件必须是外部的、确定的。
- 上下文会增长，压缩必须发生在请求边界，而不是模型内部。
- 用户插话需要在 turn 边界注入，而不是打断正在进行的调用。
- 子 agent 本质是一次带 parent 的执行，复用 effect 和 journal 比新引擎便宜。

**代价**：策略之间有交互，需要统一的策略求值顺序。

**改变条件**：如果产品需要多 agent 协商，那属于 L3 的拓扑设计，仍然不需要新引擎。

### 5.8 MCP：工具来源，不是子系统

**决策**：MCP 工具转换成普通工具，注册进 L1 的同一个工具集合；工具定义随 run 持久化。

**原因**：

- 对模型来说，MCP 工具和本地工具没有区别，都是函数调用。
- 统一后，审批、足迹、录制、回放都自动生效。
- 服务端可能离线或变更，所以工具定义必须快照进 journal，否则回放不可重复。

**代价**：MCP 的动态工具集合同步需要额外处理。

**改变条件**：如果 MCP 提供的是资源订阅或长连接事件，那部分需要独立的 effect 类型。

### 5.9 Skill：提示 + 工具，不是运行时

**决策**：skill 是可发现的文本资产。系统提示里列出名称和描述，模型通过一个加载工具按需读取正文。

**原因**：

- skill 的价值是“模型在合适时机读取一段指令”，不是新的控制流。
- 按需加载比一次性塞进提示更省 token，也更符合 Agent Skills 格式。
- 文本资产可以被产品团队独立编辑，不需要改代码。
- 快照进 run 后，回放不依赖磁盘。

**代价**：模型可能不加载正确的 skill；需要在提示和描述质量上投入。

**改变条件**：如果 skill 需要附带可执行工具或权限，那它应该扩展成“工具包”，由工具注册表管理。

### 5.10 持久化模型：事件溯源 + 检查点

**决策**：追加日志记录事实，检查点保存“快照 + 游标”。恢复时加载快照，再重放游标之后的事件。

**原因**：

- 纯事件溯源恢复时间随日志增长，长任务不可接受。
- 纯快照会丢失中间事实，无法精确回放和审计。
- 两者结合，恢复时间有上界，事实又完整。

**代价**：快照和日志的一致性需要小心；快照体积需要控制。

**改变条件**：如果 run 都很短，只保留日志即可；如果日志极大，可以只保留检查点之间的差异。

### 5.11 恢复语义：至少一次 + 幂等

**决策**：未完成的 effect 可能重新执行。工具通过幂等键或声明副作用等级来处理。

**原因**：

- 跨进程没有分布式事务，恰好一次做不到。
- 承认至少一次，才能把复杂度放在工具边界，而不是全局。
- rig 自己的恢复语义也是这个方向：中断的调用带标记，由策略决定继续还是停。

**代价**：每个有副作用的工具都要设计幂等或人工确认。

**改变条件**：如果所有工具都是只读的，这个问题消失。

### 5.12 恢复策略：按 effect 性质三分

**决策**：有开始无结果的 effect 分三种处理：重试、失败、转人工。

**原因**：

- 只读和幂等工具可以安全重试。
- 有副作用且不可幂等的工具重试会造成真实损失。
- 人工确认是唯一能覆盖未知情况的兜底。

**代价**：需要工具声明自己的类别；策略需要产品配置。

**改变条件**：如果所有副作用都在一个可控事务系统里，可以统一走补偿。

### 5.13 回放与重跑分离

**决策**：回放不调用外部服务，只返回记录的结果；重跑重新执行。两者是不同模式。

**原因**：

- 回放用于测试、审计、复现 bug，必须确定。
- 重跑用于验证变更，必须真实。
- 混在一起会导致“以为在回放，其实调用了外部服务”。

**代价**：回放需要严格的记录匹配；缺记录时必须报错，不能静默降级。

**改变条件**：无。

### 5.14 调度确定性：声明顺序优先

**决策**：并行节点的结果按声明顺序合并，不按完成顺序；分支条件是纯函数；effect id 确定性生成。

**原因**：

- 提示词顺序影响模型输出和缓存命中；完成顺序会让结果不可复现。
- 确定性 effect id 让回放能按 id 匹配，也能做去重。
- 纯函数分支让同一份日志重放出同一个路径。

**代价**：并行度受合并顺序约束；非确定性输入需要显式建模。

**改变条件**：如果产品需要“最快完成者胜”的语义，那应该是一个显式的竞争节点，而不是默认行为。

### 5.15 可观测性：三个平面

**决策**：trace、metrics、journal 三个平面，共享关联 id。metrics 覆盖五组指标：用量、调用次数、接口状态、工具执行、执行与持久化健康度。

**原因**：

- trace 回答“这次调用慢在哪、错在哪”。
- metrics 回答“用了多少、调了多少次、外部服务是否健康、工具是否正常”。
- journal 回答“到底发生了什么、能否重放”。
- 三者消费者不同、保留期不同，合成一个会互相拖累。

**代价**：需要在关键边界统一打点；id 必须贯穿。

**改变条件**：如果只是内部工具，trace 加简单日志就够。

### 5.16 内容策略：默认只记元数据

**决策**：默认不记录 prompt 和 completion 正文；需要时显式开启并脱敏。

**原因**：

- 正文可能含个人信息、密钥、业务数据。
- 存储和传输成本高。
- 元数据已经足够定位问题。

**代价**：排查某些问题时需要临时开启。

**改变条件**：如果产品运行在完全可控的隔离环境，可以默认开启。

### 5.17 不引入 Bevy

**决策**：控制平面用普通 async 运行时，不用 ECS。

**原因**：

- 三种场景不需要实体级并发和帧调度。
- Bevy 的版本锁会传导到整个产品依赖树。
- ECS 的调试和部署复杂度对集成组件是负担。

**代价**：需要自己实现调度和并发，但规模远小于 ECS。

**改变条件**：产品本身就是 Bevy 应用，或者需要运行中介入每一帧。

### 5.18 应用层：只做用例生命周期

**决策**：L4 只负责创建、恢复、取消、订阅，不实现执行细节。

**原因**：

- 用例生命周期和执行语义变化频率不同，混在一起会让执行层被产品需求污染。
- 单一入口保证所有场景共用同一套持久化和观测。
- 宿主只依赖 L4，替换 UI 或接入方式不影响内核。

**代价**：L4 需要为不同用例提供少量适配，但不允许出现业务分支。

**改变条件**：如果产品只有一种入口，L4 可以退化成一个模块而不是独立层。

### 5.19 对外接口：五个入口

**决策**：创建运行时、运行一次 agent、运行一次工作流、恢复一次执行、订阅观测事件。取消是运行句柄的方法，不单列为入口，因为它总是针对一个已经创建的执行。

**原因**：

- 集成组件的稳定性来自窄边界。
- 宿主不应该知道 run 状态、journal 格式、effect id。
- 窄接口容易测试、容易替换实现、容易跨语言包装。

**代价**：宿主需要定制时，需要提供扩展点而不是直接改内部。

**改变条件**：如果产品深度依赖内部状态，可以增加少量查询接口，但不暴露写入口。

### 5.20 版本化

**决策**：run 格式、journal 事件、workflow 定义、节点 schema 都带版本。

**原因**：

- 回放旧 run 必须用旧图。没有版本就无法区分。
- 持久化格式是长期契约，升级必须有明确路径。
- rig 自己的 run 状态已经用格式号拒绝了不兼容数据，这是正确做法。

**代价**：每次破坏性变更都要写迁移。

**改变条件**：无。

### 5.21 会话与 run 分离

**决策**：session 是长期对话，run 是一次执行；一个 session 有多个 run。

**原因**：

- 恢复语义不同：session 恢复上下文，run 恢复执行位置。
- 混用会导致“重试一次调用”变成“重放整段对话”。
- 会话可以跨产品、跨入口复用。

**代价**：需要维护两者的关联 id。

**改变条件**：如果产品只有一次性任务，不需要会话。

### 5.22 单次调用与前两种场景共用一条栈

**决策**：单次调用不另开通道。它要么是 L2 的一步执行单元，要么是只有一个节点的 L3 工作流；两者共用 L1、L0 和横切面。

**原因**：

- 如果单次调用走独立通道，持久化、观测、审批、回放都要再实现一遍。
- 共用栈意味着“简单场景”和“复杂场景”的行为一致，迁移只需改编排，不改执行。
- 代码路径可以优化，但语义模型必须统一。

**代价**：单次调用会经过一点用例层代码，但可以走单节点捷径。

**改变条件**：如果单次调用的性能要求极端，可以在 L4 做直通优化，但不得绕过 L1 和 L0。

### 5.23 被否决的方案及原因

| 方案 | 否决原因 |
|---|---|
| 整仓 fork 并重写 rig-core | provider 覆盖广、录制测试多，重写成本高，收益低 |
| 直接用 rig-ecs 当内核 | 绑定 Bevy 版本，面向终端编码 agent，ECS 复杂度对集成组件是负担 |
| 用高层 Agent + hooks 做持久化 | hook 在进程内，崩溃即丢，无法在 turn 边界可靠落盘 |
| 自建一套图引擎，rig 只当 provider | 需要另建消息、工具、effect 类型，和 rig 的录制/回放割裂 |
| 每个场景一套引擎 | 持久化、观测、审批重复实现，行为不一致 |
| 只存快照，不存日志 | 丢失中间事实，无法精确回放和审计 |
| 只存日志，不存快照 | 长任务恢复时间随日志增长，不可控 |
| 用数据库事务保证恰好一次 | 跨外部服务没有事务，代价远高于收益 |
| 图节点用运行中的对象表示 | 不可序列化、不可校验、不可迁移、不可跨语言 |
| 默认记录所有 prompt 和输出 | 隐私风险和存储成本，且元数据已足够定位问题 |
| 把 MCP 做成独立子系统 | 录制、回放、审批、观测都要再做一套，行为容易不一致 |

### 5.24 人工介入：统一中断点

**决策**：人工介入统一为三类门：工具门（工具 effect 之前）、模型门（模型调用之前和响应之后）、节点门（节点开始前和跳转前）。门决定是否发起一个人工 effect；该 effect 由 L1 调度，`begin` 写 `human_requested`，`settled` 写 `human_answered`，中间有检查点。恢复时按记录下来的决策继续。

**原因**：

- 如果三类介入各做一套审批，持久化、回放、观测、超时处理都要重复实现，行为必然不一致。
- 审批可能持续数小时甚至数天，不能靠进程内回调，只能靠持久化中断。
- 三类门都落在已有的边界上，不引入新的执行路径；门只是策略，人工交互本身仍是一条 effect。
- 决策作为事件记录后，回放能复现同一个分支，审计也能回答“谁在什么时候批准了什么”。

**代价**：检查点更密；三类门的策略求值顺序必须固定，否则同一份日志可能走出不同路径。

**改变条件**：如果只需要工具审批，可以只保留工具门，模型门和节点门作为扩展点。

### 5.25 服务器宿主：无状态 worker + 单写者 run

**决策**：服务器宿主采用无状态 worker、共享存储、单写者 run。run 的 journal 和检查点放在共享存储；同一 run 同一时刻只有一个 worker 持有租约；恢复可以由任意 worker 接管。

**原因**：

- 常规服务器应用需要水平扩展和滚动发布，进程内状态不能作为执行状态的来源。
- 人工审批可能长时间挂起，持有进程等审批不可行。
- 单写者保证 journal 追加顺序和 effect 去重；没有它，两个 worker 可能重复执行同一个 effect。
- 租约让崩溃检测和接管有明确边界，而不是靠“谁先连上谁写”。

**代价**：需要租约、围栏令牌和共享存储延迟；本地文件后端只适合单进程开发。

**改变条件**：单进程部署可以改用本地存储并取消租约，但 journal 格式和恢复语义不变。

## 6. 三个场景如何落在同一栈上

### 6.1 场景一：单次 agent 调用

路径：L5 → L4 → L2 → L1 → L0。

组成：

- 一个 run。
- 一个执行单元：一步执行或多步循环，轮数由预算限定。
- 一个工具集合：本地工具 + MCP 工具 + skill 加载工具。
- 一个 journal。
- 一个可选的会话。

流程：

```
输入 → run_started（含工具/skill 快照）
     → 调用模型（写 effect）→ 模型响应
     → 执行工具（每个工具写 effect）→ 结果回填
     → 下一轮，直到结束或预算耗尽
     → run_finished
```

为什么这样设计：

- 单次调用不需要图。多一层编排只会增加恢复和观测的复杂度，所以 L4 可以直接进 L2。
- 工具、MCP、skill 都落在 L1，工具门和模型门落在 L2，所以审批、录制、回放自然覆盖。
- 单次调用也可以在任何模型调用或工具调用前挂起等待人工，恢复后从当前 turn 继续。
- 快照让这次调用在 MCP 服务离线、skill 文件变化后仍可回放。

### 6.2 场景二：图结构

路径：L5 → L4 → L3 → L2 → L1 → L0。

组成：

- 工作流定义：节点、边、状态 schema、版本。
- 解释器：选择节点、执行、合并、检查点。
- 节点类型：模型、Agent、工具、分支、并行、合并、子图。
- 人工介入不是节点类型，而是三类门：工具门、模型门、节点门。
- 模型节点和工具节点在 L2 里是单次执行单元；Agent 节点在 L2 里是多步执行单元。

执行模型：

- 每个节点是一个可序列化的描述。
- 节点执行产生的运行时状态单独存放在工作流状态里。
- 节点完成后写节点事件，记录输出和下一节点。
- 并行用 Fork / Map / Join：Fork 声明固定并行分支，Map 对数组 fan-out，Join 按声明顺序合并。
- 子图用节点路径前缀隔离作用域，子图内部的节点门只管子图自己的边界。
- 工具门和模型门在节点内部挂起，节点门在节点开始前或跳转前挂起。
- 任一门挂起时写 human_requested 和检查点；恢复时按 human_answered 继续。

为什么这样设计：

- 图是数据，所以能存、能校验、能迁移、能由产品配置生成。
- 解释器统一处理检查点、重试、取消、观测。
- 节点之间只传 JSON，所以图可以跨进程、跨语言。
- 每个节点都复用 L2 的执行单元，不重复实现执行。

### 6.3 场景三：自主循环

路径：与场景一相同，L2 装配更多策略。

组成：

- 一个执行单元：多步 agent 循环，轮数预算较大。
- 四组策略：停止、预算、压缩、转向。
- 工具门在每次工具调用前，模型门在每次模型调用前后。
- 可选的子 agent。
- turn 边界检查点。

为什么这样设计：

- 自主性是策略组合，不是新执行模型。
- 停止条件必须在外部，因为模型不能可靠自停。
- 压缩发生在请求边界，因为限制来自模型窗口。
- 转向在 turn 边界注入，避免打断进行中的调用。
- 子 agent 是带 parent 的 effect，复用记录和观测。

## 7. 持久化详细设计

单次调用和长任务用同一套事件，没有“短任务不记录”的例外。短任务也要有 run 开始、effect 事件和 run 结束，否则“可重复”只对部分执行成立。

### 7.1 事件类别

| 事件 | 何时写 | 关键字段 |
|---|---|---|
| run_started | run 创建 | run_id、workflow 版本、输入、工具快照、skill 快照 |
| node_started | 节点开始 | node_id、attempt、输入摘要 |
| effect_begin | 外部调用前 | effect_id、处理器、类型、请求摘要 |
| effect_settled | 外部调用后 | 结果或错误、用量、时长 |
| node_finished | 节点结束 | 输出、下一节点、状态变更 |
| checkpoint | 定期或节点边界 | 游标、状态快照 |
| human_requested | 人工 effect 开始 | gate 类型（tool/model/node）、作用域、问题、选项、默认值、超时 |
| human_answered | 人工 effect 结束 | 决策、理由、编辑后的参数 |
| run_finished | run 结束 | 输出或错误 |

### 7.2 恢复流程

1. 找最新检查点。没有就从空状态开始。
2. 加载快照，重建工作流状态和 run 状态机。
3. 重放游标之后的日志，补齐状态。
4. 处理在途 effect：
   - 有结果：直接使用，不重复调用。
   - 无结果：按工具类别选择重试、失败或转人工。
5. 处理未完成的人工 effect：
   - 只有 human_requested：保持挂起，等待决策。
   - 有 human_answered：应用决策，继续。
6. 从当前节点或当前 turn 继续。

### 7.3 失败矩阵

| 崩溃位置 | 日志状态 | 恢复动作 | 风险 |
|---|---|---|---|
| effect_begin 之前 | 无记录 | 重跑节点 | 无 |
| effect_begin 之后、副作用之前 | 有开始无结果 | 重试 | 无 |
| 副作用进行中 | 有开始无结果 | 按类别处理 | 可能重复副作用 |
| 副作用之后、settled 之前 | 有开始无结果 | 按类别处理或人工 | 可能重复副作用 |
| settled 之后、检查点之前 | 有结果 | 重放直接使用 | 无 |
| human_requested 之后、answered 之前 | 有请求无决策 | 保持挂起 | 无 |
| human_answered 之后、恢复之前 | 有请求有决策 | 重放应用决策 | 无 |
| 检查点写入中 | 可能半条记录 | 拒绝半条，回到上一个检查点 | 回退一个节点 |

### 7.4 为什么不用数据库事务

- 跨外部服务没有事务。
- 追加日志比多表更新更容易保证单写者顺序。
- 日志可以后置导入数据库做查询，不影响执行路径。

## 8. 可观测性详细设计

### 8.1 五组指标

可观测性要回答五类问题，对应五组指标：

| 组 | 回答 | 典型问题 |
|---|---|---|
| 用量 | 花了多少 | 这次 run 用了多少 token，哪个模型最贵 |
| 调用次数 | 做了多少次 | 调了几次模型、几次工具，是否有循环 |
| 接口状态 | 外部服务是否健康 | 哪个 provider 在超时、限流、报错 |
| 工具执行 | 工具是否按预期工作 | 哪个工具失败、被拒、参数错误、重复执行 |
| 执行与持久化 | 系统本身是否可靠 | 检查点是否在写、恢复是否成功、是否有积压 |

为什么分成五组而不是一张大表：五组的消费者不同（产品、财务、SRE、工具作者、平台），保留期和聚合维度也不同。混在一起会让每类人都要看大量无关字段，最后谁都不看。

### 8.2 关联链

```
workflow_run_id
  → node_id
    → agent_run_id
      → turn
        → effect_id
          → provider_request_id
```

关联链的作用：任意一个指标都能沿这条链回溯到具体的一次调用、一条日志、一个工具结果。没有关联链，指标只能看总量，不能定位单次执行。

### 8.3 用量指标（token）

| 指标 | 维度 | 来源 | 用途 |
|---|---|---|---|
| input_tokens | provider、model、run、node、turn | 模型响应 | 成本、窗口占用 |
| output_tokens | 同上 | 模型响应 | 成本、生成量 |
| cache_read_tokens | 同上 | 模型响应 | 缓存命中收益 |
| cache_creation_tokens | 同上 | 模型响应 | 缓存写入成本 |
| reasoning_tokens | 同上 | 模型响应 | 推理模型成本 |
| total_tokens | 同上 | 上述求和 | 预算 |
| budget_consumed / budget_remaining | run、node | L2 预算策略 | 停止条件 |
| context_utilization | turn | input_tokens / 模型窗口 | 压缩触发 |
| compaction_saved_tokens | run | 压缩策略 | 压缩效果 |

原因：

- 不同 provider 的 usage 字段不同，必须在 L1 归一化成同一组字段，否则上层无法比较和做预算。
- 预算和成本必须基于同一份 usage，不能各算一套。
- cache 读写单独记，因为价格和普通 token 不同，混在一起会算错成本。
- `context_utilization` 是压缩策略的输入，不只是展示指标。

### 8.4 调用次数指标

| 指标 | 维度 | 来源 |
|---|---|---|
| model_calls_total | provider、model、status | 模型 effect |
| tool_calls_total | tool、status | 工具 effect |
| agent_turns_total | run、node | L2 |
| workflow_nodes_total | node 类型、status | L3 |
| retries_total | reason（provider、坏参数、坏工具调用、输出 schema） | L1 / L2 |
| invalid_tool_calls_total | tool、reason | L2 |
| human_interventions_total | gate 类型（tool/model/node）、状态（等待、通过、拒绝、超时） | L2 / L3 |
| duplicate_effect_total | tool | 持久化面 |

原因：

- 调用次数同时是成本和行为的指标。
- 重试按原因拆开，才能区分“网络抖动”和“模型不会用工具”。
- 重复 effect 计数是持久化正确性的早期信号。
- 人工介入次数反映自动化程度和产品体验。

### 8.5 接口状态指标

| 指标 | 维度 | 来源 |
|---|---|---|
| request_duration | provider、model、endpoint、stream/unary | L1 计时 |
| first_token_latency | provider、model | 流式 effect |
| http_status_class | provider、2xx/3xx/4xx/5xx | transport 结果 |
| provider_error_kind | rate_limit、auth、timeout、server、decode、transport | 错误归一化 |
| rate_limit_remaining / retry_after | provider | 响应头 |
| provider_request_id | provider、run、effect | 响应元数据 |
| decode_errors_total | provider、wire 版本 | L1 |

原因：

- “接口状态”和“agent 逻辑”必须分开。否则模型表现差时，无法判断是提示问题还是 provider 降级。
- HTTP 状态类别和错误种类要分开：4xx 里既有鉴权错误，也有参数错误，处理方式不同。
- `first_token_latency` 是流式体验的关键指标，和总时长不是一回事。
- `provider_request_id` 是唯一能把本地日志和 provider 侧记录对上的字段。

### 8.6 工具执行指标

| 指标 | 维度 | 来源 |
|---|---|---|
| tool_status | tool、每次调用 | 工具 effect 结果 |
| tool_duration | tool | L1 计时 |
| tool_output_bytes | tool | 归一化结果大小 |
| tool_error_kind | tool、错误类型 | 工具错误归一化 |
| tool_refused_total | tool、策略 | 审批或策略决策 |
| tool_denied_total | tool、策略 | 审批拒绝 |
| tool_skipped_total | tool | 跳过（无效参数、未执行） |
| tool_timeout_total | tool | 取消或超时 |
| tool_dedup_hits | tool | 幂等键命中 |
| pairing_errors_total | run | 调用与结果配对校验 |

工具状态至少包含：invoked、succeeded、failed、refused、denied、skipped、invalid_args、timeout、cancelled、uncertain（恢复时无法判断是否已执行）。

原因：

- 工具是副作用发生的地方，状态必须比“成功/失败”更细。
- `refused` 和 `denied` 是策略行为，不是错误，不能混进失败率。
- `uncertain` 是断点续跑的核心状态，必须单独计数。
- 输出大小用于成本、截断和上下文分析。

### 8.7 执行与持久化健康度

| 指标 | 来源 | 用途 |
|---|---|---|
| run_status | L4 | 运行、挂起、完成、失败、取消 |
| node_status | L3 | 节点级进度 |
| checkpoint_count / bytes | 持久化面 | 恢复成本和存储 |
| journal_bytes / events | 持久化面 | 增长趋势 |
| journal_write_errors | 持久化面 | 可靠性告警 |
| recovery_count / duration | 持久化面 | 崩溃频率和恢复能力 |
| inflight_effects | L1 | 长时间未完成的调用 |
| suspended_runs | L4 | 等待人工的积压 |
| interrupt_pending / wait_duration | L2 / L3 | 等待人工的门数量和等待时长 |

原因：持久化是硬要求，它本身必须可观测。否则“有日志”不等于“能恢复”。

### 8.8 指标从哪里来

| 数据 | 来源 | 进入哪个平面 |
|---|---|---|
| 用量 | 模型响应 | 指标 + journal |
| 调用次数 | effect 事件 | 指标 + journal |
| 接口状态 | transport 结果 | 指标 + trace |
| 工具状态 | effect 结果 + 策略决策 | 指标 + journal |
| 执行进度 | run 和 node 事件 | journal + trace |
| 持久化健康 | journal 和检查点写入 | 指标 |

规则：指标不是独立采集的，而是从 effect 事件和 journal 事件投影出来。原因：独立采集会产生第二套事实，和 journal 对不上；投影保证同一事实只有一种解释。

### 8.9 打点位置

| 位置 | 层 | 产生 |
|---|---|---|
| run 创建、结束、挂起 | L4 | run 状态、节点数、总用量 |
| 节点开始、结束 | L3 | 节点状态、节点耗时 |
| 模型调用前后 | L1 | 用量、接口状态、耗时 |
| 工具调用前后 | L1 | 工具状态、耗时、输出大小 |
| 重试 | L1 / L2 | 重试次数和原因 |
| 人工介入 | L2 / L3 | 门的等待、通过、拒绝、超时 |
| 检查点 | 持久化面 | 检查点大小、恢复点 |

### 8.10 三个平面的分工

| 平面 | 内容 | 保留期 | 采样 |
|---|---|---|---|
| Trace | span 树、耗时、错误、接口状态 | 短到中 | 头部采样，错误全留 |
| Metrics | 五组指标的聚合 | 长 | 聚合 |
| Journal | 业务事实、可回放 | 按合规要求 | 不采样 |

为什么不能合成一个：

- trace 面向单次诊断，量大、保留短。
- metrics 面向趋势和告警，只保留聚合值。
- journal 面向审计和恢复，必须完整。
- 三者的写入路径和保留策略不同，合并会互相拖累。

### 8.11 看板与告警最小集

看板：

1. run 时间线：节点、模型调用、工具调用、重试、人工介入。
2. provider 健康：错误率、p95 延迟、限流次数。
3. 工具健康：状态分布、失败率、超时率。
4. 成本：按 run、用户、租户、模型的 token 和估算费用。
5. 持久化健康：journal 增长、检查点大小、恢复次数。

告警：

- provider 错误率或 p95 延迟超过阈值。
- 工具失败率或 `uncertain` 数超过阈值。
- run 的 token 预算接近耗尽。
- journal 写入失败。
- 恢复失败或恢复时间超过阈值。
- 同一 run 长时间无进展（循环检测）。

### 8.12 隐私

- 默认只记元数据。
- 正文显式开启，开启前脱敏。
- 指标只带维度和数值，不带正文。
- `request_id` 和 `effect_id` 可以进日志，鉴权信息不可以。

### 8.13 为什么这些指标必须现在设计

- token 和调用次数是预算和停止策略的输入，不是事后报表。晚做会导致预算逻辑和观测逻辑各算一套。
- 工具状态里的 `refused`、`denied`、`uncertain` 直接对应恢复和审批策略。晚做会导致恢复时无法判断该重试还是转人工。
- 接口状态决定重试策略。没有错误分类，重试只能一刀切。
- 持久化健康是硬要求的自检。没有它，断点续跑只是“有文件”。

## 9. 模块划分与接口

### 9.1 模块与层一一对应

| 模块 | 层 | 职责 |
|---|---|---|
| your-core | L0 | 复用 rig 类型；定义 run、node、journal 事件、工作流描述的稳定类型 |
| your-call | L1 | Effect 调度；模型、工具、MCP、skill、人工交互 |
| your-exec | L2 | 执行单元：单次执行、AgentRun 循环、停止/预算/压缩/转向、工具门/模型门、工具来源装配 |
| your-graph | L3 | 工作流校验、解释器、分支、并行、子图、节点门 |
| your-app | L4 | 五个用例入口：创建、运行 agent、运行工作流、恢复、订阅 |
| your-persist | 横切面 | Journal、Checkpoint、Replay、SessionStore、中断记录 |
| your-observe | 横切面 | Trace、指标、observation、关联 id、导出 |

### 9.2 依赖方向

```
your-app
  ├─→ your-graph ─→ your-exec ─→ your-call ─→ your-core
  ├─→ your-exec
  ├─→ your-persist ─→ your-core
  └─→ your-observe ─→ your-core
```

- `your-persist` 和 `your-observe` 只依赖 `your-core`，被各层通过端口调用。
- `your-graph` 只调用 `your-exec`；模型节点、工具节点和 Agent 节点在 `your-exec` 里都是执行单元。
- `your-app` 不实现执行逻辑，只组合用例。
- 适配器在 `your-app` 的组装处注入，不进入层内。

### 9.3 端口与适配器

| 端口 | 定义位置 | 适配器 |
|---|---|---|
| 模型调用 | your-call | rig provider wire/driver |
| 工具执行 | your-call | 本地工具、MCP 客户端 |
| 持久化 | your-persist | 文件、SQLite、对象存储 |
| 观测 | your-observe | OTLP、Prometheus、标准输出 |
| 会话 | your-persist | rig-memory 的存储后端 |

端口存在的理由：测试可以换成假实现；部署可以换后端；上层不依赖具体实现。

### 9.4 对外接口

- 创建运行时。
- 运行一次 agent。
- 运行一次工作流。
- 恢复一次执行。
- 订阅观测事件。

宿主只拿运行句柄：状态、取消、事件流。不拿内部状态。

## 10. 演进路线与验收

| 阶段 | 内容 | 设计验收 |
|---|---|---|
| M0 | 单次调用骨架，内存 journal | 在模型调用和工具调用之间序列化恢复，结果一致 |
| M1 | 文件 journal、录制、回放 | 同一份日志回放两次事件序列一致；缺记录报错 |
| M2 | MCP、skill、快照、工具门 | MCP 离线仍可回放；新增 skill 不改代码；工具审批可跨进程挂起和恢复 |
| M3 | 图 v1：线性、分支、并行、合并、子图、节点门 | 并行分支和子图内崩溃后恢复，不重复已完成 effect；节点跳转可挂起 |
| M4 | 自主循环：预算、停止、压缩、转向、模型门、子 agent | 长任务重启后预算和停止仍生效；模型调用前后的门可挂起和恢复 |
| M5 | 五组指标与三平面：用量、调用次数、接口状态、工具状态、持久化健康 | 一次 run 的 token、调用次数、接口错误、工具状态都能在 trace、看板和日志中对上 |
| M6 | 生产化：保留、迁移、并发、鉴权 | 旧 run 可回放；并发写有单写者保护 |

每阶段的验收都是行为验收，不是代码完成度。

## 11. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| rig 上游 API 变化 | 集成层需要跟进 | 只依赖稳定子集；边界处做适配 |
| 图的数据化失去编译期检查 | 运行时错误增多 | schema 校验 + 图加载时校验 + 测试 |
| 日志增长 | 存储和恢复成本 | 分段、压缩、检查点、保留策略 |
| 至少一次执行 | 重复副作用 | 幂等键、工具分类、人工兜底 |
| 策略交互复杂 | 行为难预测 | 固定策略求值顺序；策略可观测 |
| 内容记录带来隐私风险 | 合规问题 | 默认关闭、脱敏、分级保留 |

---

## 12. 已确认的关键决策

| 决策 | 结论 | 设计影响 |
|---|---|---|
| 宿主形态 | 常规服务器应用 | 不引入 Bevy；L2/L3 用普通 async 运行时；无状态 worker + 共享存储 + 单写者 run（5.25） |
| 人工介入范围 | 工具审批、模型调用、节点跳转 | 统一中断点：工具门、模型门、节点门（5.24）；三类门共用 human_requested / human_answered 和检查点 |
| 图 v1 范围 | 并行和子图都要 | M3 包含 Fork / Map / Join、Subgraph 和节点门；调度与恢复覆盖并行分支和子图作用域 |

由此确定：

- 不使用 rig-ecs，按 L2 自建执行层。
- 人工介入不是可选插件，是持久化协议的一部分。
- 并行和子图进入第一版，M3 的验收必须覆盖并行分支崩溃恢复和子图内挂起恢复。

仍待确认（不影响主设计）：

- journal 和检查点的首个存储后端：本地文件、SQLite 还是对象存储。
- 是否需要多租户隔离；如果需要，run_id 和存储分区要带租户维度。

## 13. 设计验证方式

这份设计不靠代码完成度验收，靠六个问题：

1. 任意一次执行，能否只凭持久化数据重建出“发生了什么”？
2. 任意一次崩溃，能否给出确定的恢复动作和风险说明？
3. 任意一次外部调用，能否在回放模式下不触达外部服务？
4. 任意一次失败，能否从 trace、指标、日志三个平面中的至少两个定位原因？
5. 任意一次 run，能否回答花了多少 token、调了多少次、哪个接口慢或错、每个工具执行成了什么状态？
6. 任意一次人工介入，能否在另一台机器、另一时间恢复，并得到同样的决策？

六个问题都能回答，架构就成立；有一个不能，说明那一层的边界还没画对。

## 14. 六条不变量

这六条是整套设计的压缩版。任何新功能如果违反其中一条，说明它放错了层。

1. **所有外部交互都是 effect，都可序列化。** 否则无法录制、回放、恢复。
2. **所有执行事实先写 journal。** 否则崩溃后无法知道发生了什么。
3. **图是数据，执行器是解释器。** 否则流程不可存、不可校验、不可迁移。
4. **上层只组合下层，不反向依赖。** 否则分层会退化成互相调用。
5. **观测是 journal 的投影。** 否则会出现两套互相矛盾的事实。
6. **人工介入是持久化中断，不是内存回调。** 否则审批不能跨进程、不能恢复。
