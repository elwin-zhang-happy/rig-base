Usage manual · rig 0.46

使用指南

这一份按「你要做的事」组织，不按目录组织。每一节给出入口、真实签名、参考位置，以及它属于哪一层。最后一节是把它改造成你项目基础框架的落地顺序。

1 先选层：你停在哪一层

四层是一条阶梯，可以停在任何一层。判断依据不是「哪层更先进」，而是你的产品需不需要在执行过程中介入。

rig-core

只要「把请求发出去，把结果拿回来」。

agent 循环自己写。默认不含 tokio，也不含内置 HTTP。

+ rig-agent

需要多轮工具调用、hook、可暂停的一次 run。

抽象单位是「一次 run」，编排逻辑归你。

+ rig-ecs

运行中要看、拦、改；多 agent；会话恢复。

Bevy 精确锁 =0.20.0，你的应用要变成 Bevy App。

+ harness / plugins

产品就是终端编码 agent，想直接改它。

RIG_HOME、settings.toml、启动协议、终端视图。

不要从 rig-harness 开始。它是最有主张的一层，内置了桌面编码 agent 的产品假设。把它当基础框架，你会为用不到的东西付出兼容成本。要用，也应该在你自己的内核跑通之后再决定。

2 依赖与 feature

有一个容易踩的点：facade 和 rig-core 的默认 feature 不一样。根包 rig 默认带 reqwest 和 agent；rig-core 默认只有 derive 和 rustls，内置 HTTP 传输是 opt-in 的。

# 只要模型与契约。内置 HTTP 需要显式打开 reqwest
rig-core = { version = "0.46", features = ["reqwest"] }

# 要 agent 循环。它本身不绑 tokio
rig-core = { version = "0.46", features = ["reqwest"] }
rig-agent = "0.46"

# 要 ECS 内核
rig-core = { version = "0.46", features = ["reqwest"] }
rig-memory = "0.46"
rig-ecs = "0.46"

# 或者直接用 facade：默认 reqwest + agent + derive + rustls
rig = "0.46"

依据：crates/rig-core/Cargo.toml 的 [features]，根 Cargo.toml 的 default = ["rig-core/default", "reqwest", "agent", "derive", "rustls"]。

你想要开什么注意
自带 HTTP 传输rig-core/reqwest不开时，from_env() 这类不指定传输的构造函数不可用
不绑 tokio用 rig-agent，自己驱动 future参考 examples/agent_no_tokio
WebSocketrig-core/websocket，原生再加 tungstenitewasm 上只有契约，没有内置后端
无 Bevy 的纯库只依赖 rig-core / rig-agent不要把 rig-ecs 拖进来「备用」

3 最小可用：一次调用

最小路径只有两件事：构造一个模型，调用它。模型是 Wire 和 Transport 的组合，构造器帮你把这两半配好。

use rig_core::completion::CompletionRequest;
use rig_core::providers::openai::{self, OpenAI};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let model = OpenAI::from_env()?.completion(openai::GPT_5_2);
    let response = model.call(CompletionRequest::new("Say hello.")).await?;
    println!("{}", response.text());
    Ok(())
}

参考：crates/rig-core/src/driver.rs 的 Model，以及 examples/frozen_api/p1_one_prompt.rs。流式版本把 call 换成 stream，逐个 Item::Event 消费，最后 finish() 拿完整响应。

想换模型供应商时，先看它是哪种方言。OpenAI-chat 兼容的厂商不要手写实现，用下一节的 Dialect；这也是仓库对 provider 的硬性要求。

4 换掉 IO：自定义 Transport

这是最有杠杆的一个扩展点。整个调用链里只有 Transport 接触 IO，所以换掉它就能得到录制、回放、代理、离线测试。

use bytes::Bytes;
use futures::stream;
use rig_core::driver::{Exchange, Model, Opened, Opening, Transport};
use rig_core::providers::openai::{self, OpenAIConfig};
use rig_core::wire::{Encoded, Wire, WireFrame};

/// 对任何 HTTP wire 重放一份录制下来的回复体。
#[derive(Clone)]
struct Replay { body: Bytes }

impl<W> Transport<W> for Replay
where
    W: Wire<Payload = Encoded, Frame = WireFrame>,
{
    fn send(&self, payload: Encoded, _exchange: Exchange) -> Opening<WireFrame> {
        let frames = payload.framing.split(&self.body);
        Opening::ready(Opened::new(stream::iter(frames.into_iter().map(Ok))))
    }
}

// 用法：wire 不变，只换 transport
let wire = OpenAIConfig::new("unused").chat(openai::GPT_5_2);
let model = Model::new(wire, Replay { body: recorded });

参考：examples/frozen_api/p8_custom_transport.rs。注意 payload.framing：帧的切分方式由 wire 决定，录制回放不用自己判断 SSE 还是 NDJSON。

5 加一种能力：自定义 Operation

当你要接的东西不是「聊天」也不是「嵌入」，而是一种新的交换，例如本地姿态估计、语音转写、自定义批处理，就用 Operation 把它声明成一个类型。声明之后，它会自动获得流式、折叠、记录、回放。

impl Operation for PoseEstimation {
    type Request = PoseRequest;
    type Event = FramePoses;
    type End = ();
    type Response = PoseTrack;
    type Fold = PoseTrack;
    type Emit = Free;

    fn fold(_: &PoseRequest, _: &mut Call<'_>) -> PoseTrack {
        PoseTrack::default()
    }

    // 在请求到达 transport 之前校验，拒绝的请求到不了网络
    fn prepare(request: PoseRequest, _: &Descriptor<'_>) -> Result<PoseRequest, ProviderError> {
        if request.frames.is_empty() {
            return Err(ProviderError::request("a pose request needs at least one frame"));
        }
        Ok(request)
    }
}

impl Fold<PoseEstimation> for PoseTrack {
    fn absorb(&mut self, poses: &FramePoses) -> Result<(), ProviderError> {
        self.frames.push(poses.clone());
        Ok(())
    }
    fn finish(self, _end: (), _reply: Reply) -> Result<PoseTrack, ProviderError> {
        Ok(self)
    }
}

再给它一个本地运行时。这里用 Local 这个 wire，它不编码任何协议，只负责把请求交给你的 transport：

impl Transport<Local<PoseEstimation>> for PoseRuntime {
    fn send(&self, request: PoseRequest, _: Exchange) -> Opening<Step<PoseEstimation>> {
        let runtime = self.clone();
        let poses = stream::iter(request.frames.into_iter().enumerate())
            .map(move |(index, frame)| Ok(Step::Event(runtime.estimate(index, &frame))));
        let end = stream::once(async { Ok::<_, ProviderError>(Step::End(())) });
        Opening::ready(Opened::new(poses.chain(end)))
    }
}

let model = Model::new(
    Local::<PoseEstimation>::new("candle-pose"),
    PoseRuntime { threshold: 0.5 },
);

参考：examples/frozen_api/p5_local_operation.rs，完整可运行。这条路径同样适用于「调用你已有的 C++ / Python 推理服务」。

6 接一个厂商：用 Dialect，不要手写

OpenAI-chat 兼容的厂商只差几个怪癖。仓库把差异做成了数据：

use rig_core::providers::openai::OpenAIConfig;
use rig_core::providers::openai::wire::{Dialect, Quirks};

pub const ACME: Dialect = Dialect::gateway("acme", "https://api.acme.test/v1", "ACME_API_KEY")
    .with_quirks(
        Quirks::openai()
            .without_stream_usage()        // 流式不带 usage
            .without_response_format()     // 不支持结构化输出
            .done_without_finish_reason(), // [DONE] 但没有 finish_reason
    );

let acme = OpenAIConfig::from_env_with(&ACME)?.client();
let model = acme.completion("acme-large");

参考：examples/frozen_api/p7_openai_compatible_vendor.rs。cargo xtask check-wires 会检查「每个 provider 是不是一条 wire」。

如果厂商不是任何现有方言，才需要手写 Wire：describe 返回描述，encode 是纯函数，decoder 每次新开。写完对照 providers/openai/wire.rs 的拆分方式，不要把所有逻辑塞进一个函数。

7 加一个工具

工具的类型参数就是它的参数结构，schema 可以从参数类型推导（args_schema），也可以手写。下面是手写版，和 frozen_api 的示例一致：

use rig_core::tool::{Tool, ToolContext};

#[derive(serde::Deserialize)]
struct AddArgs { a: i64, b: i64 }

#[derive(Debug, thiserror::Error)]
#[error("math error")]
struct MathError;

struct Add;

impl Tool for Add {
    const NAME: &'static str = "add";
    type Args = AddArgs;
    type Output = i64;
    type Error = MathError;

    fn description(&self) -> String { "Add two integers.".into() }

    fn parameters(&self) -> serde_json::Value {
        serde_json::json!({
            "type": "object",
            "properties": { "a": { "type": "integer" }, "b": { "type": "integer" } },
            "required": ["a", "b"]
        })
    }

    async fn call(&self, _ctx: &mut ToolContext, args: AddArgs) -> Result<i64, MathError> {
        Ok(args.a + args.b)
    }
}

注册分两套。用 agent 运行时，把工具放进 ToolSet 或 agent builder；用 ECS 内核，注册到 App：

use rig_ecs::prelude::*;

let mut app = App::new();
app.add_tool(Add);

ECS 侧：rig_ecs::tools::AppToolsExt::add_tool（crates/rig-ecs/src/tools.rs:244）。工具 future 跑在 Bevy 的 async compute 池上，阻塞操作要自己挪到独立线程（rig-tools 的 blocking 就是这么做的）。

8 用 agent 运行时

三种用法，控制力从低到高。多数场景停在第一种。

8.1 Builder 加 hook

use rig_agent::agent::{
    AgentBuilder, AgentHook, HookContext, ModelTurnAction, ModelTurnFinished,
};

struct RetryOnMarker { marker: &'static str }

impl AgentHook for RetryOnMarker {
    async fn on_model_turn_finished(
        &self,
        _ctx: &HookContext,
        event: ModelTurnFinished<'_>,
    ) -> ModelTurnAction {
        // 检查 event.content，决定继续、重试还是停止
        ModelTurnAction::Continue
    }
}

let agent = AgentBuilder::new(model)
    .preamble("You are a careful reviewer.")
    .add_hook(RetryOnMarker { marker: "REJECT" })
    .build();

参考：examples/agent_with_retry_hook。AgentHook 覆盖 run 开始、模型选择、请求前、回合结束、无效工具调用、事件分发、最终结果。默认实现全是放行，只实现你要的那几个。

8.2 在运行时追加 hook

let response = agent
    .prompt("What is 2 + 5?")
    .max_turns(2)
    .add_hook(ToolLoggerHook)
    .run()
    .await?;

8.3 自己驱动状态机

AgentRun 是 sans-I/O 的：它只告诉你「现在该调模型」还是「现在该跑工具」，IO 由你做。它最有价值的性质是工具调用挂起时整个状态可序列化：

use rig_agent::run::AgentRun;

// 挂起：把整个 run 存下来
let suspended = serde_json::to_string(&run)?;

// 恢复：换一个进程也行，待执行的工具调用会从状态里重新发出
let mut run: AgentRun = serde_json::from_str(&suspended)?;

参考：examples/agent_run_stepping/src/main.rs，前半段是手驱循环，后半段是 hook 版。人工审批、跨进程恢复、断点续跑都建立在这个性质上。

9 用 ECS 内核

内核不碰视图也不碰文件系统，所以启动它只需要两样注入：一个会话存储，一个模型来源（测试里可以用脚本模型）。

9.1 最小 App

use rig_ecs::prelude::*;
use rig_ecs::session_log::SessionStore;
use rig_memory::MemoryStore;

let mut app = App::new();
app.insert_resource(SessionStore::new(MemoryStore::default()))
    .add_plugins((AgentPlugin, SessionLogPlugin))
    .add_tool(Add);

// 测试里推进一帧即可，不需要 ScheduleRunner
app.update();

依据：crates/rig-ecs/src/lib.rs 的 crate 文档示例。

9.2 加一条策略：阶段里的普通 system

审批、限额、路径限制都不需要改内核。写一个查 EffectRequest 的系统，放进 Gate 阶段，写 Decision 即可：

use rig_ecs::prelude::*;

fn no_deploys(mut effects: Query<(&EffectRequest, &mut Decision), (ReadyToStart, PluginEffects)>) {
    for (request, mut decision) in &mut effects {
        if request.kind.name() == "deploy" {
            decision.decide(
                Decider::plugin("no-deploys"),
                Outcome::refused("no deploys today"),
            );
        }
    }
}

app.add_plugins(AgentPlugin)
    .add_systems(AgentPass, no_deploys.in_set(Stage::Gate));

参考：crates/rig-ecs/src/stage.rs 的模块文档。要观察或改写结果用 Stage::Review；要挂起一个 effect 用 HoldOf。

9.3 加一个宿主动作

你自己的副作用（部署、发通知、调内部服务）不要绕过 effect 通道。声明一个 CustomEffect，它就会和模型调用一样被记录、被审批、被回放：

use rig_core::effect::CustomEffect;

impl CustomEffect for Deploy {
    const KIND: &'static str = "deploy";
    type Answer = DeployOutcome;
}

参考：crates/rig-core/src/effect/mod.rs:293；处理与记录的完整例子在 crates/rig-harness/PLUGINS.md 的 Effects of a plugin's own 一节（约第 1267 行）。

9.4 换存储

实现 rig_memory::Files 加 Store（同步）或 AsyncStore（网络、JS promise），内核不关心后面是什么。注意会话日志有格式版本，StoreOpener 会拒绝别的格式。参考 crates/rig-memory/src/store.rs:53。

11 把它改造成你的基础框架：落地顺序

不要一上来就 fork 整仓。三步试错，每一步都有明确的验收标准和不通过就回退的条件。

Step 1：只碰 rig-core

依赖 rig-core 加 reqwest，照 p5 和 p8 写一个你自己的 Operation 和一个 Transport，用录制的数据跑通。

验收：在不修改 rig 源码的前提下，你能表达自己的模型能力，并且同一份数据既能实时跑也能回放跑。如果这一步就卡住，说明你需要的是改 wire 或 driver 的内部，直接进入 B 模式（vendor 快照），别再往上加层。

Step 2：起一个 headless 内核

按 9.1 起一个 App，加一个工具、一条 Gate、一个 MemoryStore，在测试里推完一个 turn。

验收：Gate 能拒绝一个工具调用，会话能落盘并恢复。如果 Bevy 带来的复杂度超过你对「可介入」的需求，回到 Step 1 停在 rig-agent。这是最常见的正确结论。

Step 3：决定怎么持有代码

按摩擦点的位置选，不按代码量选：

摩擦点模式做法
都在扩展点里（wire、tool、gate、store）A 依赖上游只用发布版，扩展写在自己的 crate
在 wire / driver / turn 的内部行为里B 快照vendor 一个固定 tag，只维护改过的文件，保留上游测试
编排模型与它结构不同（例如图编排是一等公民）C fork保留 core / agent / ecs / memory / cassette，丢掉 harness、cli、plugins、corpus

验收：你能写出一份「我们会改的文件清单」。如果超过 10 个文件，说明你在跟上游结构对抗，重新考虑切割线。

如果选 C，先确认 bevy = "=0.20.0" 与你的项目不冲突。这是唯一的硬阻塞：Bevy 版本是精确锁，不是范围。

12 约束与坑

坑现象处理
rig-core 默认没有 reqwestfrom_env() 找不到或没有默认传输显式开 features = ["reqwest"]，或者改用 facade rig
Bevy 精确锁 =0.20.0与已有 Bevy 项目版本冲突，Cargo 无法同时满足把 rig-ecs 隔离到独立 crate；或不上 ECS 层
MSRV 1.97.1老工具链编译失败固定 rust-toolchain.toml，CI 用同一版本
feature 统一是全局的你的 JSON 键顺序或浮点解析行为被别的 crate 改变在 workspace 根显式声明 serde_json 的 feature，别依赖默认
会话格式有版本StoreOpener 拒绝别的格式，升级即迁移尽早冻结自己的格式；或只用自己的 store
pre-1.0 破坏性变更每周都可能改 API锁一个快照 tag，不追 main；升级时看 MIGRATING.md
仓库 lint 很严fork 后 unwrap / expect / 索引都会报错，测试也一样接受它，或者只在你自己的 crate 里放宽
工具阻塞会占线程async compute 池被 std::fs 或 Command 卡住阻塞工作挪到独立线程，照 rig-tools 的 blocking

最后一条使用建议：把 examples/frozen_api/ 的八个程序当成你的改造基线。它们钉住的正好是你要接的八个方向；每次改动之后跑一遍，比读文档可靠。
