Rig · contract architecture

五个契约，一个调用骨架

rig-core 把「调一次模型」拆成五个互相不认识的契约。这张页说明它们各自被什么驱动、谁实现、以及在哪个点上被装配起来。所有数字取自当前工作树。

图 1 · type lattice

契约之间是参数化关系，不是分层关系

每一个契约锚定在一个独立的变化源上。它们在类型上互相引用：Wire 绑定一种 Operation，Transport 绑定一个具体的 Wire，Model 把后两者配成一对。DynModel 是这套参数在运行时的擦除形式。

图 2 · call path

一次调用经过谁

左侧标签是每一步的契约归属。stream 与 call 走的是同一条路径，只在最后一步分开。call 就是「开一条流，再把它读完」。

图 3 · dialects

厂商差异落在数据里

OpenAI 方言有 25 个常量，但只有一个 Chat wire。每家厂商把差异写成一份 Quirks，编码器读这份数据，而不是被复制 25 遍。

why

乘法被拆成加法

三个正交维度相乘时，一个具体类型要同时知道操作、协议和传输。拆开之后每个轴各写一遍，交叉处由泛型承担。

Rust 不能给别人的类型加方法，所以「行为注入」也只能落在 trait 上，SpanCombinator、Lenient 这类单实现契约就是这么来的。

merge candidates

哪些可以合

判据很简单：实现数 ≥ 3 且跨 crate，是边界，别动；只有 1 个实现且没有外部实现者，是合并候选。

按这个口径，VectorDistance、ToolCallback、TextProcessor 可以直接变成方法；Clock 是故意的注入点，留下来。

extend

加一家厂商要做什么

写一个 const Dialect：名字、base URL、环境变量名、一份 Quirks。真正的协议差异用 DialectHooks 的四个函数指针补。

不要新写 completion model、请求结构体或消息转换，那是这套契约明确禁止的做法。
