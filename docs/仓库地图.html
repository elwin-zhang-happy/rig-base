仓库地图

一张依赖图回答「谁依赖谁」，两张架构图分别回答「库怎么把模型变成请求」和「编码 agent 怎么被启动起来」。 所有边都来自各 crate 的 Cargo.toml path 依赖，不是推测。

图 1 · dependency

依赖图：一个地基，两套栈

左边是库栈（provider、向量库、记忆、经典 agent 运行时），右边是编码 agent 栈（Bevy 内核加插件）。 两套栈几乎不互相依赖，只在 rig-core、rig-memory、rig-tools 这几块地基上汇合。

聚合说明：plugins/* ×9 是 rig-basics、rig-tui、rig-acp、rig-mcp-client、rig-steel、rig-inspect、rig-traffic、rig-claude-cloak 与 corpus 之外的 9 个插件 crate； 编码内核 合并 rig-ecs、rig-harness、rig-tools；provider + 向量库 ×18 合并 6 个自有 SDK provider（bedrock、vertexai、gemini-grpc、candle、fastembed、typesafeai）与 12 个向量库 crate。 dev-dependencies 与部分 feature 门控的边从略；rig-core 的 25 个依赖方是逐 crate 数出来的实数。

图 2 · library architecture

库架构：一次调用怎么走到网络上

rig-core 把「模型」拆成三段：配置构造 wire（某个 API 方言的请求与响应编解码），Model 再把 wire 绑定到 driver::Transport（真正发请求的东西）。 rig-http 只定义契约，rig-reqwest 与 rig-tungstenite 是自带实现。

rig-core 里 provider 专属的 wire 直接住在 src/providers/（openai、anthropic、gemini、ollama、deepseek 等）， 因为它们只是既有方言的变体，必须复用共享的 generic completion model；需要自有 SDK 的 provider 才拆成独立 crate。 rig-derive 的两个 derive（Embed、ContextValue）与 12 个向量库对 VectorStoreIndex 的实现从略。

图 3 · agent architecture

编码 agent：启动链与运行时

rig 二进制本身几乎不做事：它读 settings，生成一个 Cargo 工程，把 settings 打开的插件编译进去，然后运行那个进程。 真正的 agent 是 Bevy app：rig-harness 提供 session 与服务，rig-ecs 提供内核，其余全是插件。

settings.toml 同时被 launcher 和 rig-harness 读取（后者的边从略）；生成的是普通 Cargo 工程，所以插件可以任意增删而不改二进制代码。 退出码 75 由 rig-harness-protocol 定义，表示「请用新构建重启我」；启动即崩的构建会被回滚到上一个可用版本。

structure

两套栈，一个地基

库栈（providers、向量库、agent 运行时）和编码 agent 栈（Bevy 内核 + 插件）几乎不互相依赖。 它们的公共点只有 rig-core、rig-memory、rig-tools： 换句话说，砍掉整个编码 agent 也不影响库里任何东西。

extension

扩展靠 feature 门控

根 crate rig 是一层 re-export：rig-core 原样重导出，每个配套 crate 是一个同名 feature 的模块。 不想带上依赖时直接依赖 rig-core，这就是为什么 provider 与向量库都拆成了独立 crate。

agent

agent 本身就是插件

终端界面、--print、内置工具、reload 都是 plugins/rig-*，只使用 rig-harness 的公共 API。 corpus 里的几十个插件语料就是用这个边界反向验证内核设计的。
