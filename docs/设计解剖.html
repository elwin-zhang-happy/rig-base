设计解剖

上半讲 rig 现状为什么这样设计：一条变化速率主轴，五个调用契约，两条执行路径，三家协议家族的归一化。下半讲改造时可以直接用的东西：代价清单、判断规则和你的切割线。调用链路的完整盘点见《调用契约》，动手步骤见《使用指南》。

1 一条主轴：变化速率

按领域分层会得到「provider 层、agent 层、存储层」。Rig 不这样分。它先问一件事：这层东西多久变一次。变得快的，做成数据；变得慢的，做成类型；几乎不变的是基础设施。依赖方向永远从易变指向稳定。

最能说明问题的是 Wire：它明明是厂商适配器，却要求 Clone + Send + Sync + Serialize + Deserialize，encode 必须是纯函数。因为厂商协议变得快，所以它不能是一个持有连接的对象，必须是一份能存进场景、写进配置、录进回放的数据。

2 五个契约与一次调用

一次模型调用被拆成五个角色，每个角色只回答一个问题：

  • Operation：这次交换的输入、事件、结束、输出分别是什么。
  • Wire：这个厂商的请求长什么样，回复怎么读。
  • Transport：字节怎么送出去、怎么收回来。
  • Driver：把上面三者绑在一起，保证流式和整包走同一条路径。
  • Effect / Serve：这次交换怎么被记录、怎么被擦除后调度。

关键的一刀是 Decoder 和 Fold 分开。Decoder 只懂「字节 → 厂商事件」，Fold 只懂「事件加结束 → 归一化响应」。两者拆开之后，流式和整包共享同一套解码与折叠逻辑，录下来的事件流也能直接重放出完整响应。

完整盘点见《调用契约》：契约之间的参数化关系、一次调用的七步路径、方言数据表和全部契约清单。

3 类型在上，数据在下

同一个代码库里并存两种表达，而且它们只在一处相接：构造期用类型保证正确，运行期用数据保证可存、可回放、可跨进程。

这条思路可以直接用在你自己的框架里：凡是需要跨进程、跨会话、可回放的东西，都不要让它以泛型类型的形式穿过边界。给它一个擦除后的数据形态，再提供一个重建入口。

4 副作用只有一条通道

模型调用、工具调用、消息投递，在 Rig 里是同一类东西：effect。所有横切关注点都挂在这一个点上，而不是散落在每个调用处。

这是 rig 现状的 effect 通道。改造目标的七阶段形态（门、挂起、journal）见《控制平面架构》图 3。

5 两条执行路径

很多人以为 rig-agent 和 rig-ecs 是新旧替代关系。不是。它们回答的是不同的问题：调用方是否需要在执行过程中介入。下面先一眼对比，再逐条展开。

AgentRun 最容易被低估的一点：它在工具调用挂起时整个状态可序列化。存下来，换一个进程恢复，待执行的工具调用会从自己的状态里重新发出。需要人工审批的流程可以直接建立在这个性质上。

5.1 库路径：rig-agent 的 run 循环

构造和执行是分开的。AgentBuilder 产出不可变的 Agent；每次 prompt 产出一个 AgentRunner，它再驱动一个纯状态机 AgentRun。状态机只决定下一步做什么，IO 由驱动层完成。

编号钩子在哪一步能做什么
1on_run_start第一次模型调用前改写提示词，或在发出任何请求前终止
2on_model_select每次 CallModel 前在已构造的模型之间选择；不能做阻塞 IO
3on_completion_call请求编码前返回请求补丁，或终止
4on_model_turn_finished模型回合结束后接受、重试（无工具回合）、终止
5on_dispatch / on_outcome工具调用前后观察、改参数、拒绝、改写结果
6on_run_settled结束后只观察，不能再调度工作

5.2 内核路径：rig-ecs 的实体与阶段

同一条请求在 ECS 里不是一个循环，而是一组实体：消息、回合、模型调用、工具调用各自是实体，每个实体在固定阶段里推进。你可以在任意阶段插一个普通 system 去观察、拦截或改写。

两条路径在模型调用处汇合成一条管线：Operation::prepare 校验请求，Wire::encode 编出请求体，Transport::send 发出去，Decoder 把帧解成事件，Fold 把事件和结束折叠成归一化响应。逐段展开见 §2 五个契约与一次调用；这里只需要记住：厂商语法只出现在 encode 和 decode 两步，前后都是归一化的。

6 七阶段：同一帧内跑到不动点

在 ECS 里，每一次「工作」都是一个 effect 实体。它在一帧之内依次经过七个阶段，任何一个阶段都可能被插件拦下、改写或挂起。跑完一轮如果还有东西在动，就再跑一轮，直到没有 effect 移动为止。

这不是回调链。回调链的问题是「谁在什么时候被调用」只能靠读框架源码回答；阶段模型的答案是「你把自己的系统加进哪个阶段」。代价是顺序敏感，所以仓库里有一个 check-stage-order 专门守这件事。

这是 rig 现状的七阶段。改造目标补齐了 Commit 先写 journal、Gate 可挂起为人工 effect 等语义，见《控制平面架构》图 3。

7 厂商接口的差异与共同点

Rig 不按「厂商」组织代码，而按「协议家族」组织。注册表里只有三个家族：OpenAI（Chat Completions 与 Responses）、Anthropic（Messages）、Gemini（GenerateContent）。其余厂商要么是这三个家族的方言，要么是自带 wire 的特例（Bedrock Converse、Cohere 原生、Ollama 原生）。

8 公共与可变的切分

切分的判据只有一句：语义归一，语法下沉；能变成数据的语法变成数据，不能的才写代码。

8.1 四层扩展阶梯

差异的性质扩展点代价例子
身份、地址、能力位、路径Dialect 常量一个 const，不改代码路径Acme 网关、DeepSeek、Groq

注意 DialectHooks 的设计：它存的是函数指针，比较的是指针地址，所以一个方言配置仍然可以序列化和反序列化。「可配置」和「可存储」在这里不冲突。

9 功能测试的拆分

Rig 的测试原则写得很直白：录制的真实流量是默认证据，合成语料不能证伪它自己的模型。 这句话决定了每一层的分工：越接近纯函数的越便宜，越接近真实流量的越有说服力。

层证据能抓抓不到
单元测试模块旁的 tests.rs编码器、解码器、结束映射、请求整形的内部逻辑真实厂商的线上格式漂移
Frozen APIexamples/frozen_api/ 8 个程序公共类型和 trait 的形状被破坏任何运行期行为
Cassette 回放fixtures/cassettes/<provider> 的 867 份录制响应解析、流式事件、出站请求体形状录制之后厂商行为的变化
Reply bank / runtime每个 provider 的真实回复形状agent 循环、工具生命周期、结束方式、恢复出站请求体
Effect goldens / verify录制回放产生的 effect 日志副作用总线、录制引擎、历史迁移网络与厂商
Live provider真 key，默认 #[ignore]厂商当前的真实行为稳定复现，成本也高
Corpus17 个只依赖公共 API 的插件包公共 API 还能不能写出现实插件provider 行为

最容易被忽略的一条：cassette 不只验证响应。它会把出站请求体也和录制比对，所以「回复处理对了，但请求形状悄悄变了」会在 mock 未命中时失败。这就是为什么它可以当作请求边界的断言层。

9.1 为什么这四层缺一不可

  • 单元测试证明「我们理解了自己的代码」。
  • cassette 证明「我们的代码能处理真实字节，并且请求没有漂移」。
  • reply bank 证明「同一套 agent 语义在每个 provider 上都成立」。
  • live 证明「provider 没有在我们背后改行为」。

再往上一层，corpus 和 frozen_api 证明「别人还能用你的 API」。这五件事各自否证不同的假设，不能互相替代。

10 封装演示：从零接一个厂商

假设你有一个 Acme 网关，它说 OpenAI Chat 方言，但流式不返回 usage，不支持结构化输出，并且结束流时只发 [DONE] 不带 finish_reason。你要写多少代码？答案是一个常量。

动手时的快速版见《使用指南》§6；下面是完整五步，证明每一层差异落在 §8 的哪个扩展点上。

第一步：能数据化的，写数据

pub const ACME: Dialect = Dialect::gateway(
    "acme",
    "https://api.acme.test/v1",
    "ACME_API_KEY",
)
.with_quirks(
    Quirks::openai()
        .without_stream_usage()
        .without_response_format()
        .done_without_finish_reason(),
);

let acme = OpenAIConfig::from_env_with(&ACME)?.client();
let model = acme.completion("acme-large");

参考：examples/frozen_api/p7_openai_compatible_vendor.rs。到这一步，鉴权、路径、能力位、结束语义全部就位，请求编码和回复解码复用的是整个 OpenAI 家族。

第二步：需要代码的，写钩子

如果 Acme 还需要「按 key 推导端点」或「每个请求加一个签名头」，不要改 wire 主体，挂到 DialectHooks：

static ACME_HOOKS: DialectHooks = DialectHooks {
    default_endpoint: Some(derive_endpoint_from_key),
    model_route: None,
    completion_envelope: Some(sign_request),
    modality_envelope: None,
};

钩子仍然挂在方言数据上，所以存下来的 wire 仍然能反序列化。这是「可变」和「可存储」之间的折中。

第三步：不是这个方言，才写 wire

如果 Acme 换了消息容器、工具块或流式事件类型，它就不是 OpenAI 方言。这时你实现 Wire，但只写三件事：encode、Decoder、可选的 Reassembler。下面这些全部复用：

  • Operation 与 Fold：事件怎么折叠成响应。
  • Model 与驱动：流式和整包同一条路径。
  • 归一化类型：Message、ToolCall、Usage、FinishReason。
  • 错误分类、重试、空闲超时、遥测。

第四步：不是 HTTP，才写 transport

Bedrock 是一个好例子：它的 wire 是 Converse JSON，但传输走 AWS SDK，帧是二进制的 event stream。它只实现了自己的 Wire 和 Transport，上层完全没有变化。

第五步：测试按层加，不要只加一种

你要证明的加什么位置
方言常量本身正确一个单元测试，断言路径、能力位、鉴权wire 模块的 tests.rs
真实字节能解析，请求不漂移一个 cassette 套件crates/rig-cassette/tests/providers/acme/
agent 循环在这个 provider 上成立把回复形状加进 reply bankfixtures/bank/

封装的好坏不体现在「支持了多少厂商」，而体现在加第 28 个厂商时你要碰几个文件。Rig 的答案是：如果是方言，一个常量加一份录制；如果是新协议，一个 wire 加一个 transport，上层零改动。

11 你可以直接抄走的抽象

如果你在自己的框架里重建这套东西，最小集合是六个类型、三张表、两个 trait、一个折叠，外加一套分层测试。

类别内容为什么是它
六个归一化类型Message、ToolCall/Result、Usage、FinishReason、StreamEvent、Error跨厂商唯一稳定的东西是语义，不是字段名
三张数据表方言身份与路径、能力位、模型事实变化快，必须能改数据而不改代码
两个 traitWire（纯函数、可序列化）、Transport（唯一 IO）把协议和 IO 彻底分开，回放才成为可能
一个折叠Fold：事件加结束 → 响应流式和整包共用一条路径
一条副作用通道所有模型调用、工具调用、宿主动作都是 effect审计、预算、审批、回放只挂一处
一套分层测试单元 → 录制回放 → 运行时场景 → live，加编译期契约每层否证不同的假设，不能互相替代

最后用一句话收束上面的解剖：流程是状态机，差异是数据，公共部分只有一个语义内核，测试按「证据离真实流量多远」分层。 你把新东西往这四条线上放，它自己就会落到正确的层。

12 内核、宿主、插件：三层边界

这是整个仓库最值得直接搬走的一个决定：内核不知道视图，也不知道文件系统。它只定义 agent、effect、阶段、会话日志；存储和模型由宿主注入。因此同一个内核可以跑 TUI、-p、ACP 和纯 library 程序。

13 契约靠消费者证明

文档会过期，注释会撒谎。Rig 的办法是让公共 API 一直有外部消费者，并且让 CI 编译它们。

14 每条拆分付的代价

这套架构不是免费的。改造之前先确认你愿意付哪些账。

决定换来了什么代价
Operation 作为泛型参数配错 wire 与 operation 编译不过单态化、签名长、入门曲线陡
Wire 是纯数据可存、可录、可换传输、可无网测试解码器要写成状态机，不能持有连接
Decoder / Fold 分开流式与整包一条路径，录制可重放多一层抽象，读代码要跟着两层走

15 改造时可以直接用的判断规则

你以后每加一个东西，先问这五个问题，答案会直接告诉你它该落在哪一层。

问题落在哪
这个变化每周都可能发生吗？数据。像 catalog 一样做成可覆盖的表，不要写进代码。
它需要一个厂商或后端的专门实现吗？纯数据加纯函数。像 Wire 一样：能序列化，encode 无副作用。
它是框架的能力契约吗（输入、事件、输出）？类型。像 Operation 一样，让编译器帮你校验组合。
它只影响一个前端或一种产品形态吗？插件。不要进内核；用公共 API 写，编译器会告诉你越界没有。
它要跨进程、跨会话、可回放吗？擦除成数据，再提供重建入口。不要让泛型类型穿过这个边界。

一句话版本：变化快的做成数据，变化慢的做成类型，只影响前端的做成插件，要跨进程的擦除成数据。

16 你的切割线

下一步是「把哪一层作为你的基础框架」。四层不是四选一的套餐，而是一条可以停在任何一层的阶梯。详细用法见配套的《使用指南》。

停在这层你拿到你必须接受
rig-core27 个 provider、12 个向量库、消息、工具、会话、模型事实agent 循环自己写；默认不含 tokio，也不含内置 HTTP（要开 reqwest）
+ rig-agentBuilder、hook 栈、可序列化的 AgentRun、记忆抽象单位是「一次 run」，编排逻辑归你
+ rig-ecs实体化 agent / 回合 / 调用、单一 effect 通道、会话恢复Bevy 精确锁 =0.20.0，你的应用要变成 Bevy App
+ rig-harness / plugins完整的终端编码 agentRIG_HOME、settings.toml、启动协议、终端视图

判断方法：如果你的产品需要在执行过程中看、拦、改，停在 ECS 这一层；如果只是「输入一段话，拿到一个结果」，停在 rig-agent，不要为了架构好看把 Bevy 引进依赖树。
